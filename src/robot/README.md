# Robot Control

Robot integration for the Dino Egg Catch Challenge. The operating modes are specified in [docs/spec/operating-modes.md](../../docs/spec/operating-modes.md). Phase 1 is implemented here: **Manual Mode** (formerly Drive Mode), in which an attendee drives the LeKiwi base with the dino-controller and/or moves the dinosaur arm with the leader arm, a mode manager driven by KachiButton phrases, and a pygame signboard that shows the overhead, front, and wrist cameras, the mode, and the drive and arm status. Rerun is an optional operator view. Manual Mode's base driving is unchanged from the earlier implementation. Phase 2 step 1 adds front-camera egg detection and the first half of **Auto Catch**: `Hi!` checks that an egg is in view at a usable size and then drives the base until the egg sits at the best position in the front image (see "Auto Catch step 1: alignment"). Phase 2 also adds **Auto Release**: `Thx` checks the pink basket, aligns the base to it, moves the arm home with the egg held, and plays a recorded release motion (see "Auto Release"). Phase 3 step 1 extends Auto Catch after the alignment: the arm moves slowly to the recorded catch pose, the wrist view is checked for the egg (disabled by default), a pick-policy stub runs, and the arm returns slowly to the release pose (see "Auto Catch: catch pose, wrist check, policy stub").

**Stubs (no motion):** the pick policy at the catch pose ("Catch: policy not available yet") and Full Self-Catching (FSC, mode "FSC (demo)") only change the signboard text. In FSC the base is sent zero velocities and the arm holds its pose.

Hardware adapters are kept separate from mode logic so behavior can be checked without moving a robot. Emergency stopping and communication-loss handling stay local (Mac application and Pi host), never behind a cloud service. Background and API references: [LeKiwi application development guide](../../docs/lekiwi-app-development.md) and [dino-controller protocol](../../docs/dino-controller-protocol.md).

## Running Manual Mode

1. On the Raspberry Pi (`pi@lekiwi`, conda env `lerobot312`, inside `~/lerobot-dino-egg-catch-challenge`):

   ```bash
   python -m lerobot.robots.lekiwi.lekiwi_host --robot.id=dino_kiwi
   ```

2. On the Mac, from this repository root, use the conda env `lerobot312` (owner decision): `conda activate lerobot312`, or call `/opt/miniconda3/envs/lerobot312/bin/python` directly. The env has the LeRobot fork installed editable (`pip install -e ".[lekiwi,viz]"` in `../lerobot-dino-egg-catch-challenge`) plus pyserial and pygame-ce. Check that it imports the fork; the path must be under `lerobot-dino-egg-catch-challenge`:

   ```bash
   python -c "import lerobot; print(lerobot.__file__)"
   ```

   The env uses `opencv-contrib-python-headless==4.13.0.92` in place of the `opencv-python-headless` that LeRobot pulls (owner-approved, 2026-09-24). Both install the same `cv2`, so the contrib wheel must replace the plain one in the same env; it adds `cv2.ximgproc` for the detector's default EdgeDrawing spot stage (without it the detector falls back to the HSV stage, which is less robust to lighting and tarp glints). The root `pyproject.toml` describes the same dependencies for an alternative `uv` setup. The leader arm calibration `dino_leader_arm.json` must be present under `~/.cache/huggingface/lerobot/calibration/teleoperators/so_leader/` (see the guide, section 3); if it is missing or does not match the motors, LeRobot prompts on the terminal at connect (press ENTER to use the file or type `c` to recalibrate) and start-up waits for that answer. `--no-leader` skips the leader arm entirely (no connect, no prompt). Then start Manual Mode:

   ```bash
   PYTHONPATH=src python -m robot.teleop_drive
   PYTHONPATH=src python -m robot.teleop_drive --fullscreen --rerun
   PYTHONPATH=src python -m robot.teleop_drive --leader-port /dev/tty.usbmodemXXXX
   PYTHONPATH=src python -m robot.teleop_drive --no-leader --controller-port /dev/cu.usbserial-XXXX --no-camera
   ```

   Options: `--no-camera`, `--no-signboard`, `--fullscreen` (overrides `SIGNBOARD_FULLSCREEN`), `--rerun` (opt-in operator view), `--controller-port`, `--remote-ip`, `--leader-port` (default `LEADER_ARM_PORT`), `--no-leader` (the arm holds its pose; Manual Mode is drive-only). Defaults come from `config.py`. Find the overhead camera index with `lerobot-find-cameras opencv` and set `TOP_CAMERA_INDEX`.

   **Overhead camera size (owner request, 2026-09-24: show the whole field of view).** The Mac camera's native mode is 1920x1080 at 30 fps (16:9), and AVFoundation center-crops a 4:3 request such as 640x480, cutting off the tarp's edges. The application therefore requests the standard 16:9 mode `TOP_CAMERA_WIDTH` x `TOP_CAMERA_HEIGHT` = 1280x720. Each loop frame downscales it once (`vision/top_frame.py`, INTER_AREA) to `TOP_DISPLAY_WIDTH` = 960 wide (960x540) for the signboard, Rerun, and captures, which keeps the signboard pipe at about 1.5 MB per frame. The raw 1280x720 frame stays in the loop for a later overhead tracker (not used yet). LeRobot's `OpenCVCamera` raises a `RuntimeError` at connect ("failed to set capture_width/height") if the camera does not deliver exactly the requested size. If that happens, set `TOP_CAMERA_WIDTH`/`TOP_CAMERA_HEIGHT` to 960x540, or else 640x360 (both 16:9, so `TOP_CAMERA_ASPECT` stays valid), or run with `--no-camera`. With `--no-signboard` there is no KachiButton input (and so no `Stop` phrase); only Ctrl+C stops the application.

   Devices are opened in this order: controller, robot (captures the arm pose to hold), leader arm, camera, signboard, Rerun. A leader arm that cannot be opened stops start-up; use `--no-leader` to run without it.

## KachiButton controls

The KachiButton types plain ASCII phrases into whichever window has keyboard focus. The signboard window keeps focus for the whole exhibit (owner decision; no global keyboard hook). The signboard child receives the text through pygame `TEXTINPUT` events, matches complete phrases (exact, case-sensitive, including spaces and punctuation; more than `KACHI_PHRASE_GAP_S` = 1 s between characters discards the partial phrase), and sends each command to the parent as one JSON line on its stdout: `{"v": 1, "type": "command", "command": "stop"}`.

| Phrase | Command | Manual Mode | FSC |
| --- | --- | --- | --- |
| `Go Go!` | `mode_toggle` | Switch to FSC (while stopped: release the Stop latch, stay in Manual Mode) | Switch to Manual Mode (while stopped: release the latch into Manual Mode) |
| `Hi!` | `hi` | Auto Catch: size precondition, base alignment, catch pose, wrist check, policy stub, release pose (below) | Toggle voice listening (display only in Phase 1: "Listening..." / "Voice input ended", `mic on` in the status bar) |
| `Thx` | `thx` | Auto Release: basket precondition, basket alignment, home, recorded release motion (below) | No action (owner decision) |
| `Stop` | `stop` | Emergency stop and reset (below) | Emergency stop and reset (below) |

Every mode switch first sends zero base velocities, clears pending encoder rotation, and disengages arm following. Presses other than `Stop` are ignored while an automatic action runs (Auto Catch, Auto Release). Notices stay for `NOTICE_SECONDS` (3 s).

**`Stop` is a latch** ([spec, section 2](../../docs/spec/operating-modes.md); owner decision, 2026-09-24). `Stop` switches to Manual Mode, cancels any action (including a running alignment), clears voice input, discards pending encoder rotation, disengages arm following, and latches the stopped state. While it holds, every frame sends zero base velocities (controller input is ignored and no rotation is queued), the arm holds its last commanded pose with torque kept on (the host only releases torque when it disconnects) and the leader is not read, `Hi!` and `Thx` are ignored, and another `Stop` keeps it stopped. The signboard shows `STOPPED` in the warning color with "Press Go Go! to resume" for as long as the latch holds. `Go Go!` releases it and always returns to Manual Mode (it does not toggle to FSC): one more zero-velocity frame, then the base follows the controller and the arm re-engages through the slow approach. Nothing moves again on its own after a stop. `Stop` does not close the application; ESC, the window close button, and Ctrl+C quit it through the zeros-first shutdown.

## Leader arm

The leader arm is an `so100_leader` on `LEADER_ARM_PORT` (`/dev/tty.usbmodem5A7A0179021`) with id `LEADER_ARM_ID` (`dino_leader_arm`), verified values from the guide. `get_action()` reports joints without the `arm_` prefix; `leader_arm.py` adds it and sends all six keys, including the gripper (the mouth).

- **Engagement (owner decision; numbers proposed):** when Manual Mode starts, after a mode switch, after `Stop`, and after a leader fault, the dinosaur arm moves toward the leader's pose at `ARM_ENGAGE_SPEED_DEG_S` (30 deg/s) per joint, starting from the last commanded pose. Real-time following begins once every joint is within `ARM_ENGAGE_TOLERANCE_DEG` (3°) of the leader. The gripper is in percent and uses the same numbers (30 %/s, 3 %). Both values are proposals to tune on the robot. The frame time used for the approach is clamped to 2 / `LOOP_HZ`, like the rotation budget.
- **Faults:** a failed read (bus error, disconnect, malformed reading) returns `None`; the arm holds its last commanded pose, following disengages so a recovered leader is approached slowly again, the base keeps working, and the signboard shows `LEADER ARM FAULT`. The adapter logs a warning once per failure streak and an info line on recovery.
- **Leader ignored:** in FSC, while the Stop latch holds, or with `--no-leader`, the arm holds its pose and the leader is not read. During Auto Catch and Auto Release the leader is not read either; the arm follows the action's phases.

## Auto Catch step 1: alignment

Owner decisions (2026-09-24): eggs are white ellipsoids with green, red, or orange spots (orange replaces blue, dropped the same day). In Manual Mode, `Hi!` looks at the newest **front camera** detection:

| Front camera at the press | Signboard (warning color, `NOTICE_SECONDS`) | Robot |
| --- | --- | --- |
| No egg detected | "No egg in view" | Nothing moves |
| Egg bbox height below `AUTO_CATCH_MIN_EGG_H` (0.15 of the frame) | "Egg too far" | Nothing moves |
| Egg bbox height above `AUTO_CATCH_MAX_EGG_H` (0.85) | "Egg too close" | Nothing moves |
| Otherwise | "Aligning...", mode line `MANUAL - AUTO CATCH` | Base aligns (below) |

There is no dialog to dismiss (attendees have no cursor): alerts are timed notices only. During the alignment the controller's base input and the leader arm are ignored (the arm holds its last pose, status `arm auto catch`), and `Hi!`, `Thx`, and `Go Go!` are ignored. The controller (`align.py`) drives the base toward the **best position**, the egg pose in the front image that the pick policy will start from: sideways from the horizontal error (egg right of the target -> move right, `-y`) and forward/backward from the error of the egg's **ellipse width** (narrower than the target = farther -> forward, `+x`; wider -> back up), no rotation. The owner's first run on the robot (2026-09-24) moved too fast and oscillated, so the owner asked for a progressive slow-down. Each axis now commands `ALIGN_MAX_XY * clamp(error / full-speed error, -1, 1)`: full speed `ALIGN_MAX_XY` (0.06 m/s, below the 0.1 m/s slow level) at `ALIGN_FULL_SPEED_ERROR_CX` (0.18) or `ALIGN_FULL_SPEED_ERROR_W` (0.15), falling linearly toward zero near the target. An axis inside its tolerance gets 0, and a command below `ALIGN_MIN_XY` (0.015 m/s) becomes 0 so the base does not creep. The egg's cx and ellipse width are smoothed with an exponential moving average (`ALIGN_SMOOTHING` 0.5 = weight of the new sample; a missing detection leaves the average unchanged). The controller and the done test use the smoothed values. Each velocity changes by at most `ALIGN_MAX_ACCEL` (0.15 m/s²) × frame time per frame. Terminal results send zeros at once. `config.py` refuses values for which the command just outside any tolerance edge (`ALIGN_MAX_XY * min(1, tolerance / full-speed error)`) would fall below `ALIGN_MIN_XY`, because the base would then stop short of "done" and wait for the timeout. With the current numbers the edge commands are 0.0167 m/s (cx), 0.016 m/s (width, far edge: 0.06 × 0.04 / 0.15, the binding one; a full-speed error of 0.25 would give 0.0096 and stall), and 0.04 m/s (width, near edge).

**Distance measure: the egg's ellipse width** (reviewer changes, 2026-09-25). The bbox height depends on the light: the shadowed underside merges with the tarp (h 0.542-0.650 at the best position). The top edge (`top = cy - h/2`) was tried next and failed on the robot (owner, 2026-09-25, capture 015558): the egg stopped much too close with top 0.221 but w 0.775 and h 0.779. The front camera's optical axis is at about the egg's top height, so the top edge sits near the horizon line (about 0.22) for every distance closer than the best position; it only moves for far eggs. Spot size (`d_med` 80-119 at one distance) depends on which spots are visible. The width grows monotonically as the egg gets closer, and the fitted-ellipse width (`EggDetection.ellipse_w`: the ellipse's horizontal extent clipped to the frame, the bbox width when there is no ellipse) has the smallest spread at the best position:

| Captures | Distance | bbox w | ellipse w | h | top |
| --- | --- | --- | --- | --- | --- |
| 220742, 225648, 225701, 230143, 010137, 010212 | best position | 0.572, 0.644, 0.637, 0.625, 0.616, 0.622 | 0.572, 0.603, 0.625, 0.602, 0.612, 0.610 (median 0.607) | 0.542-0.650 | 0.217-0.225 |
| 220336, 220404, 230437, 232411 | mid | 0.422, 0.428, 0.425, 0.362 | 0.420, 0.430, 0.410, 0.354 | 0.400-0.423 | 0.260-0.267 |
| 222325, 003436 | far | 0.286, 0.295 | 0.285, 0.286 | 0.296, 0.312 | 0.273 |
| 015558 | very close | 0.775 | 0.756 | 0.779 | 0.221 |

On 220742 both widths read 0.572 (the edge fence trims the rim beyond the edge spots); on the red eggs the ellipse ignores spots bulging past the outline. The too-far / too-close check at the `Hi!` press still uses h, the Auto Release basket path still uses its bbox width, and the trace keeps h and top for analysis.

**Asymmetric width window** (owner feedback, 2026-09-24: closer is fine, farther is not). The egg counts as aligned in distance while `ALIGN_TARGET_W_EGG - ALIGN_TOL_W_FAR` <= ellipse width <= `ALIGN_TARGET_W_EGG + ALIGN_TOL_W_NEAR`, that is 0.567-0.707 with `ALIGN_TARGET_W_EGG` 0.607, `ALIGN_TOL_W_FAR` 0.04, and `ALIGN_TOL_W_NEAR` 0.10. Inside the window the x axis commands 0; narrower (farther) drives forward, wider backs up (015558 at 0.756 would back up). The cx tolerance stays symmetric at `ALIGN_TOL_CX` 0.05.

**If it still oscillates.** The Pi JPEG stream adds roughly 100-200 ms of latency, so the controller always reacts to a slightly old image. Lower `ALIGN_MAX_XY` or `ALIGN_MAX_ACCEL`, raise the full-speed errors, or lower `ALIGN_SMOOTHING` (heavier smoothing adds lag of its own). If that is not enough, the next step is move-stop-observe: drive for a short burst, stop, wait for a fresh frame, repeat. That mode is not implemented yet.

**Trace for tuning.** While aligning, the loop appends one row per frame (`t, cx_raw, w_raw, h_raw, top_raw, cx_smooth, w_smooth, x_vel, y_vel, result`; `w` is the ellipse width) to `captures/<YYYYmmdd-HHMMSS>-align.csv` (stamp = alignment start; one line written per frame) and logs the path when the run ends. A failed write is logged once and tracing stops for that run; the alignment continues.

The run ends with **done** after `ALIGN_DONE_FRAMES` (10) consecutive frames with the smoothed egg within `ALIGN_TOL_CX` (0.05) and the asymmetric width window (above): zeros, then the arm phases below (the trace file ends here); **lost** after `ALIGN_LOST_FRAMES` (30, 1 s) consecutive frames without an egg: warning "Egg lost". Until then the controller keeps steering toward the last smoothed position and the in-tolerance count is kept (neither advanced nor reset), because a far egg can flicker in and out of detection (robot run 2026-09-24); **timeout** after `ALIGN_TIMEOUT_S` (15 s): warning "Could not align". Lost and timeout send zero velocities for that frame and return to Manual Mode with arm following disengaged, so the arm re-syncs to the leader slowly.

**Detection.** The detector runs every frame in Manual Mode on the front frame, in the parent process. It is anchored on the spots and scaled by their size, and it does not rely on the spot color being distinct from the background. Under strong light, glints on the tarp's wrinkles are as white as the egg (capture 223853), and the blue egg's spots had exactly the tarp's color (captures 231156/231202). Blue eggs were then dropped, but the edge-based spot stage they motivated stays the default for lighting robustness. All tunables are in `vision/config_vision.py`.

1. **Masks** (`vision/egg_masks.py`): the white body and one mask per spot color, with the pink basket removed.
   - Body (`EGG_BODY_HSV`): S <= 50 at any hue, plus warm whites (H 0-40) up to S 65 (the warm egg white under room light reaches S 61-65). Bright bluish tarp reflections (S 50-65) stay out.
   - Green is H 35-90 (spot hue medians 76-82), S >= 60, V >= 15.
   - Red is H 0-7 or 170-179 with S >= 100 and V >= 25. Under the light of 010137/010212 the red spots drop to S 95-118 (p10) and H 172. The low-end hue never exceeded H 4 (p99).
   - Orange is H 8-25, S >= 120, V >= 60. This is a placeholder until the painted orange egg is captured.
   - The basket (`BASKET_HSV`) is H 150-169 at S >= 60, plus H 170-179 only below S 100, so it never overlaps red. The body and the green and orange masks drop the whole basket; the red mask drops only the first range. Basket and red spots share H 170-176 at S 100-182. The white-ring spot test, same-color clusters, and the cap keep basket pixels out of eggs; the basket-only captures give no egg.
2. **Spots:** `EGG_SPOT_DETECTOR = "edge"` (default, needs `opencv-contrib-python-headless`) runs EdgeDrawing ellipse detection (`vision/spot_edges.py`). An ellipse becomes a spot only if all three hold: its minor axis is at least `EGG_MIN_SPOT_DIAMETER_PX`; it is surrounded by egg white: at least `EGG_RING_WHITE_FRACTION` (0.35) of the in-frame ring from 1.15x to 1.6x its axes is white. True spots measured 0.48-0.89; a patch of tarp scores near 0. most of its inside is one spot color (`EGG_EDGE_SPOT_MIN_FILL` 0.5).

   The white ring, not the color, separates a spot from background of a similar color: tarp, glints, or the dropped blue egg's spots. `"hsv"` (connected components of the color masks) remains as the fallback without `cv2.ximgproc`.
3. **Clusters:** spots of the same color link when their centers are closer than `EGG_SPOT_CLUSTER_FACTOR` (4.0) × the larger spot diameter. The edge stage often finds only an egg's outer spots, up to ~4.5 d apart. A cluster's scale `d` is the median diameter of its core spots, those at least `EGG_CORE_SPOT_FACTOR` (0.35) × its largest spot. Clusters with `d` below `EGG_MIN_SPOT_DIAMETER_PX` (10 px) are skipped.
4. **Segmentation per cluster** (`vision/egg_detector.py`):
   - Inside a window around the core spots, grown by `EGG_WINDOW_FACTOR` (2.0) × `d` per side, the body OR the cluster's accepted spot interiors is closed (`EGG_CLOSE_KERNEL_PX`, the shell's crack) and opened with `EGG_OPEN_SPOT_FACTOR` (0.5) × `d`, which removes glints thinner than half a spot.
   - **Edge fence** (`vision/egg_refine.py`): a white wall, a white PVC pipe, or clothes behind the field touch the egg and pass the body mask (captures 010137/010212), so after the crack close, Canny edges of the window's V channel (`EGG_FENCE_CANNY` 40/120, dilated by `EGG_FENCE_DILATE_PX` 3) are removed. The egg's shaded silhouette then separates it from a flat white background. The fence is not applied inside the convex hull of the core spots' pixels, so the crack and the spot borders do not cut the egg apart.
   - The component touched by the most core spots (center or a ring just outside each spot) is kept. It gets back its own half of the fence band (3 px + 1). Where a spot sits on the silhouette, the thin rim beyond it stays fenced off, so boxes can be a few px narrower.
   - **Hull cap:** the component is cut to the convex hull of the core and missed spots, grown by `EGG_HULL_CAP_FACTOR` (1.4) × `d`. On all check captures the egg bbox reaches at most 1.0 d past its core spots.
   - Spots the spot stage missed are added from the color mask: pixels of the cluster's color inside the component's convex hull, plus whole spot-sized (<= `EGG_SPOT_BLOB_MAX_FACTOR` × a spot's area) and compact (`EGG_SPOT_BLOB_MIN_EXTENT`) blobs touching it, so spots on the egg's edge are not cut. Tarp of the same color is larger and stays out. Morphology runs on a downscaled copy so kernels stay near 15 px.
5. **Rules:**
   - At least `EGG_MIN_AREA_PX`, bbox aspect in `EGG_ASPECT_RANGE`, and scale (bbox height / `d`) in `EGG_SCALE_RANGE` (1.8-6.5; 3.1-4.3 for the green egg, 2.46-2.86 for the red egg, whose two big spots dominate).
   - The outline is gap-repaired, then needs solidity >= `EGG_MIN_SOLIDITY` (0.85) and, away from the frame border, fitted-ellipse fill in `EGG_ELLIPSE_FILL_RANGE` (0.75-1.25).
   - Spots: at least `EGG_MIN_SPOTS` blobs and `EGG_MIN_SPOT_FRACTION` (0.12) of the egg area, measured from the cluster's color inside the egg (0.215-0.306 on the eleven captures).
6. **Result:** the color with the most spot pixels names the egg, and overlapping results from two clusters are merged. With several eggs in view, Auto Catch uses the largest by area (`best_egg`), which is normally the nearest one. The size precondition, alignment, and overlay all follow that egg (capture 232411: a green egg in front, a far red egg at the frame edge).

Each detection carries its bbox, which alignment and the size precondition use, and the ellipse fitted to the repaired outline (`EggDetection.ellipse`: center, axes, angle), which the signboard and the inspect tool draw. The Auto Release basket detector uses its own, looser range (see "Auto Release"). The detector needs about 10-12 ms per frame on the captures. The signboard's front view always shows the target as an egg-shaped outline labelled "place the egg here" just below it (also a guide for attendees driving by hand), and the best egg's fitted (possibly rotated) ellipse as a green outline ("green egg", label above it) when its size is usable, or as an accent-colored outline ("green egg: too far") otherwise. The detector's average time over the first 30 frames is logged once at INFO.

**Pi camera colors.** `LeKiwiClient` returns the front and wrist frames RGB-ordered (see `PI_CAMERA_COLOR_ORDER` in `config.py` for the verified chain in the fork); the loop converts them to BGR once, right after `observe()`, so the detector, the signboard, captures, and Rerun all get BGR like the overhead camera.

**Values are placeholders to calibrate at the venue.** The best position (`ALIGN_TARGET_CX` 0.49 from 220742, `ALIGN_TARGET_W_EGG` 0.607 from the best-position group above; `ALIGN_TARGET_CY` 0.53, `ALIGN_TARGET_W` 0.57, and `ALIGN_TARGET_H` 0.61 only draw the guide) is the detector's own measurement of capture `20260924-220742`, taken by the owner with the egg at the best position, so target and detector agree. The detector values were checked against the captures `20260924-220742`, `20260924-220336`, `20260924-220404`, `20260924-222325`, `20260924-223853`, and the red-spotted `20260924-225648`, `20260924-225701`, `20260924-230143`, `20260924-230437`, and the two-egg `20260924-232411`. The blue-spotted `20260924-231156` and `20260924-231202` are a regression: no egg of another color may be reported there. The tolerances and speeds are proposals. Recalibrate at the venue:

The raw front and wrist frames (640x480) and the top frame (downscaled to 960x540) are saved as `captures/<YYYYmmdd-HHMMSS>-{front,wrist,top}.png` with `<stamp>.json` (detections with normalized bbox, color, and size class, plus the mode); the notice says "Captured". `captures/` is git-ignored.

## Auto Catch: catch pose, wrist check, policy stub

Owner decisions (2026-09-25, [spec, sections 1 and 4](../../docs/spec/operating-modes.md)): the arm has two recorded poses, the **release pose (home)** `data/arm/home_pose.json` (head up; driving and Auto Release) and the **catch pose** `data/arm/catch_pose.json` (head down; the wrist camera sees the aligned egg). At the `Hi!` press, after the size check: `catch_pose.json` missing or invalid -> "Catch pose not recorded", `home_pose.json` missing or invalid -> "Home pose not recorded" (warning; nothing moves). **Start pose (owner decision, 2026-09-25):** the leader can leave the arm in any pose (head low or forward), and driving during the alignment or a straight joint-space move to the catch pose from there could sweep the head through the egg; release -> catch is the known-safe path. So when any non-gripper joint of the commanded pose is farther than `POSE_NEAR_TOLERANCE_DEG` (15°) from the release pose, Auto Catch first moves the arm there (phase `to_start`, base at zero, gripper held; 8 s limit: "Arm did not reach the release pose", action ends), then aligns; near it, the alignment starts at once. `CATCH_VIA_RELEASE_POSE` (default True) is kept only as a maintenance switch. After the alignment (`robot/auto_catch.py`; mode line `MANUAL - AUTO CATCH: to start pose / aligning / to catch pose / checking / to release pose`, arm status `arm auto catch`):

1. **To catch pose:** base zero; every joint and the gripper (the mouth opens as recorded) approach the catch pose at `ARM_ENGAGE_SPEED_DEG_S`, done within `ARM_ENGAGE_TOLERANCE_DEG`. After `RELEASE_HOME_TIMEOUT_S` (8 s): warning "Arm did not reach the catch pose", then step 3.
2. **Wrist check:** the arm holds for `WRIST_CHECK_FRAMES` (10) frames. With `WRIST_CHECK_ENABLED`, the loop runs `vision/wrist_check.py` on the wrist frame in those frames only; no egg in any of them -> warning "Egg not in wrist view", then step 3. Disabled (the default) or an egg seen -> **policy stub:** "Catch: policy not available yet" (info); no arm motion.
3. **To release pose:** the joints approach the release pose with the gripper held at its current value (as Auto Release's home phase), same speed, tolerance, and timeout ("Arm did not reach the release pose"). Done: "Ready" after a pass through the policy stub; after a failure in step 1 or 2 its warning is shown again instead, so it survives the return. Then back to Manual Mode with arm following disengaged (slow re-sync to the leader).

`Stop` cancels it in every phase in the frame it arrives (zeros, arm held, Stop latch); the controller and the leader are ignored while it runs. **Recording the catch pose (staff):** in Manual Mode with `arm following`, put the arm head down over an egg at the best position with the leader and press `k` (`CATCH_POSE_KEY`): "Catch pose saved" (same file format as the home pose; refused with "Cannot record: ..." outside Manual Mode, when the arm is not following, or while an action runs; a failed write shows "Catch pose not saved").

**Wrist check (disabled by default, `WRIST_CHECK_ENABLED = False` in `vision/config_vision.py`).** It is a spot-only close-up mode (`vision/wrist_check.py`). At the catch pose the egg fills the view and is cut by the border, so none of the front camera's egg-shape rules apply. The egg is present when at least `WRIST_MIN_SPOTS` (1) spot passes all of these checks:
- it is an EdgeDrawing ellipse or an ellipse-fitted HSV colour blob;
- it is disk-like: minor axis >= `WRIST_MIN_SPOT_PX` (40) and axis ratio <= `WRIST_MAX_SPOT_ASPECT` (1.5);
- it is filled with one egg colour (>= `WRIST_SPOT_MIN_FILL` 0.7);
- it is ringed by egg white on >= `WRIST_RING_WHITE_FRACTION` (0.5) of the in-frame part of its ring, with >= `WRIST_RING_MIN_INSIDE` (0.25) of the ring inside the frame.

The white gripper parts have no spots, and the teal gripper part and the pink basket edge are not disks and have no white ring. The result gives the colour of the largest accepted spot and the centroid of the accepted spots. It is `partial` when an accepted spot, or the white region around it, touches the border. On the owner's wrist captures (2026-09-25): `20260925-014442` (near egg) gives a red egg, partial; `20260925-014418` (far egg) and `20260925-014506` (no egg) give no egg. It takes 13–15 ms per frame and runs only during the 10 wrist-check frames. The accepted spot's ring is 0.60 white against the 0.5 threshold, a thin margin to watch.

**The wrist check is diagnostic only (owner decision, 2026-09-25).** The wrist camera is mounted at an angle, so the aligned egg sits at the edge of the wrist view and a far-but-aligned egg leaves it entirely (014418); centering it is impractical and unnecessary because the pick policy also sees the joint state. `WRIST_CHECK_ENABLED` therefore stays False: Auto Catch does not gate on the wrist view. The close-up detector remains available for diagnostics (`c`, then `PYTHONPATH=src python -m robot.vision.inspect captures/<stamp>-wrist.png --wrist`) and for a possible signboard indicator later.

**Phase 3 handoff.** The pick policy is a stub: `pick_stub` is where the policy runner will start from the catch pose with the egg in the wrist view. Demonstrations are recorded from the catch pose with `PYTHONPATH=src python -m robot.recording.record_pick_egg --egg-color green` (the fork's `record_loop` with the leader arm and keyboard, behind a start-pose gate before every episode); the prerequisites, gate, key map, reset procedure, and the `lerobot-record` compatibility note are in the [development guide, section 6](../../docs/lekiwi-app-development.md).

## Auto Release

Owner decisions (2026-09-24, [spec, section 4](../../docs/spec/operating-modes.md)): `Thx` in Manual Mode is a one-shot action. The pink basket must be in the front camera; then the base aligns to the basket with the Auto Catch controller (so the recorded motion always starts from the same relative pose), the arm moves to the home (base) pose with the gripper unchanged so the egg stays held, a recorded release motion (a fixed joint trajectory from the leader arm, not a learned policy) delivers the egg and opens the mouth, and the arm returns home. **Reviewer safety choices (owner confirmation pending):** playback runs at `RELEASE_PLAYBACK_SPEED` (0.5 of the recorded speed; 1.0 = recorded, allowed range (0, 2]), every joint change is capped per frame, and playback starts only after the base has been sent zeros for the whole home phase. Checking that the egg really landed in the basket is out of scope for this step.

| At the `Thx` press | Signboard (warning color) | Robot |
| --- | --- | --- |
| No basket detected | "Basket not in view" | Nothing moves |
| Basket bbox width below `AUTO_RELEASE_MIN_BASKET_W` (0.30; never "too close") | "Basket too far" | Nothing moves |
| `data/arm/home_pose.json` missing or invalid | "Home pose not recorded" | Nothing moves |
| `data/arm/release_motion.json` missing or invalid | "Release motion not recorded" | Nothing moves |
| Otherwise | "Aligning to basket...", mode line `MANUAL - AUTO RELEASE` | Phases below |

1. **Align:** `align.py` with the basket target (`RELEASE_TARGET_CX` 0.53, `RELEASE_TARGET_W` 0.80; the size measure is the bbox width), tolerances `RELEASE_TOL_CX` 0.05, `RELEASE_TOL_W_FAR` 0.04, `RELEASE_TOL_W_NEAR` 0.10, and the egg path's speeds, smoothing, rate limit, frame counts, and timeout. Lost: "Basket lost"; timeout: "Could not align".
2. **Home:** base zero; every joint except the gripper approaches the home pose at `ARM_ENGAGE_SPEED_DEG_S`; done within `ARM_ENGAGE_TOLERANCE_DEG`. After `RELEASE_HOME_TIMEOUT_S` (8 s): "Arm did not reach home".
3. **Play:** "Releasing..." and the progress in percent on the mode line. The motion is time-scaled by `RELEASE_PLAYBACK_SPEED` and resampled at `LOOP_HZ`, one pose per loop frame. Its first frame is approached slowly first when the arm is farther than the tolerance (8 s limit: "Arm did not reach the release start"). Every joint, the gripper included (this is where the mouth opens), moves at most `RELEASE_MAX_JOINT_STEP_DEG_PER_S` (90) × frame time per frame; the last frame is reached exactly.
4. **Return home:** all joints including the gripper approach the home pose (same speed, tolerance, and timeout), then "Released!" and back to Manual Mode; the arm re-syncs slowly to the leader.

While it runs, the controller's base input and the leader arm are ignored, the arm status is `arm auto release`, and `Hi!`, `Thx`, and `Go Go!` are ignored. `Stop` cancels it in every phase in the frame it arrives: zeros, arm held where it is, Stop latch. Every end sends zero velocities for that frame.

**Basket detector** (`vision/basket_detector.py`, about 1.3 ms per frame): `BASKET_DETECT_HSV` (H 158-179, S 30-200, V >= 18) is looser than the egg detector's `BASKET_HSV` exclusion (unchanged), because at the release position the basket is dark (V 40-52) and desaturated (S median 49-77). The mask is downscaled by 2, opened (`BASKET_OPEN_PX` 11 full-resolution px; removes red egg spots, which are pink-ish but 1-2 % of the frame) and closed (`BASKET_CLOSE_PX` 25), and the largest component counts when it covers at least `BASKET_MIN_AREA_FRACTION` (0.05) of the frame and fills at least `BASKET_MIN_FILL` (0.35) of its bbox. The signboard draws it as a pink rectangle labelled "basket" in Manual Mode, and the basket target as a thin rectangle only while Auto Release runs. `inspect --basket` prints and draws it.

**Recording the data (staff, from the signboard keyboard, Manual Mode, leader arm following).** The keys are KEYDOWN like `c`: `b` (`HOME_KEY`) and `r` (`RECORD_KEY`). Not `h`: the KachiButton types the "h" of "Thx" and "Hi!" as key presses, so every press would overwrite the home pose.

1. Wait for `arm following`. Put the arm in the home pose (neck folded, head pointing up; owner decision 2026-09-24) with the leader and press `b`: "Home pose saved" (`data/arm/home_pose.json`, the commanded pose).
2. Hold an egg at home and drive the robot to the release position in front of the basket (as in captures 232927/232953; the alignment will reproduce it).
3. Press `r`: "Recording release...", then "REC release N s" in the warning color. Move the leader from home over the basket, open the mouth, and stop there (the return home is automatic).
4. Press `r` again: "Release motion saved (N frames, T s)" (`data/arm/release_motion.json`; the previous one is kept as `release_motion.prev.json`). Fewer than two frames: "Recording too short".
5. Recording is refused outside Manual Mode ("Cannot record: not in Manual Mode") or when the arm is not following (no leader, syncing, stopped, an action running: "Cannot record: arm not following"), and cancelled with nothing written if following stops meanwhile ("Recording cancelled"). A failed write shows "Home pose not saved" / "Release motion not saved".
6. Review and commit both files. The first physical test runs at 0.5x with a hand on `Stop` and nobody near the arm.

**Data files** (JSON, written atomically; each carries a `"note"`): `home_pose.json` is `{"version": 1, "recorded_at": "<ISO time>", "note": "...", "pose": {<the six arm_* keys>: <float>}}`; `release_motion.json` is `{"version": 1, "recorded_at": ..., "note": ..., "rate_hz": 30, "frames": [{"t": 0.0, "pose": {...}}, ...]}` with `t` in seconds since the recording started (strictly increasing, at least two frames). Loading rejects anything else. No data files are committed yet: they must be recorded on the robot.

## Display

The attendee display is a pygame window (owner decision, 2026-09-24): the overhead camera large on the left, the front and wrist cameras stacked on the right (the front view with the Auto Catch overlays), and a three-line status bar. The main panel is exactly as tall as a `TOP_CAMERA_ASPECT` (16:9) image of its width needs (at 1280x720: 821x462), and the two 4:3 side views stack in the same height. The status bar takes the remaining height: 210 px at 1280x720, never less than `SIGNBOARD_STATUS_HEIGHT` (96). Its fonts are `SIGNBOARD_FONT_SIZE` 44 and `SIGNBOARD_SMALL_FONT_SIZE` 28. Line 1 (large) is the mode: `MANUAL` or `FSC (demo)`, followed by the running action when there is one (with the Auto Catch phase, or the playback progress in percent during the Auto Release motion), or `STOPPED` while the Stop latch holds. Line 2 is "Press Go Go! to resume" while stopped; otherwise the current notice if present; otherwise "REC release N s" while the release motion is recorded; otherwise, in Manual Mode, the drive status (`DRIVE`, `INPUT LOST`, and `CATCH!` only if the Catch role is re-enabled), and in FSC the voice hint "Press Hi! to talk" or "Listening... (Hi! to end)" (the controller is not used in FSC, so its status is not shown there). Line 3 is the arm status (`arm holding`, `arm syncing`, `arm following`, `LEADER ARM FAULT`, `no leader arm`, `arm auto catch`, `arm auto release`), `mic on` while FSC voice input is toggled on, the speed level as footprints (fixed by config), and the held directions plus a rotation symbol (↺/↻, ASCII `CCW`/`CW`) while an encoder rotation is pending. The bar turns the warning color while stopped, while the release motion is recorded, while a warning notice is shown (a rejected Auto Catch, "Egg lost", "Could not align", "Capture failed"), and, in Manual Mode, on input loss. A missing frame shows "no signal". Unicode symbols are used only when pygame's default font has them; otherwise ASCII fallbacks (`#`/`-`, `UP`/`RIGHT`) are shown.

The signboard runs as a separate interpreter (`python -m robot.signboard_process`, started by `SignboardClient`) because opencv (pulled in by LeRobot) and pygame each bundle their own `libSDL2` on macOS, and both copies cannot safely live in one process. The control loop sends it one packet per loop frame over the child's stdin; only the newest packet is kept, so the loop never blocks on the display. KachiButton commands come back on the child's stdout (nothing else is written there; logs go to stderr) and are collected by a reader thread into a queue that the loop drains each frame. The parent process never imports pygame and the signboard process never imports LeRobot or cv2; tests assert both.

The window has no buttons, and ordinary keys do not control the robot: only complete KachiButton phrases do. The extra staff keys are `c` (`CAPTURE_KEY`, saves a capture), `b` and `r` (Auto Release data, above), and `k` (catch pose, above); `config.py` refuses staff keys that a KachiButton phrase contains. ESC or the window close button (or the signboard process exiting for any reason) ends the application through the normal shutdown, so zero velocities are sent before disconnecting. The colors in `DEFAULT_THEME` are a placeholder Jurassic palette; artwork (wood-sign frames, fonts, footprint icons) will come later as image assets.

| Rotary encoder | Rotate right (cw) / left (ccw); one click turns the base by half the knob's own angle per click (360° / detents × 0.5; currently assumed 20 detents = 9°), open-loop; the detent count needs the counted test. Encoder clicks add a rotation budget in degrees; each frame the loop sends `theta.vel = ±theta` and subtracts what that speed covers in the measured frame time (clamped to 2 / `LOOP_HZ`). `ENCODER_DEGREES_PER_STEP` is derived as `360 / ENCODER_CLICKS_PER_REVOLUTION * ENCODER_ROTATION_SCALE` (scale 0.5, owner decision 2026-09-24). `ENCODER_CLICKS_PER_REVOLUTION = 20` is a placeholder until the detent count is measured (see "Detent calibration", still pending in [dino-controller-validation.md](../../docs/dino-controller-validation.md)). This is commanded, not measured, rotation, so the real heading change also depends on the wheels and floor. Rotating while translating is allowed. Contradictory directions cancel. Every command also carries six arm positions, because the fork's host fails on actions without arm keys (code reading, not tested on the robot): the pose captured at connect until the leader arm is engaged, then the commanded leader pose, and the last commanded pose whenever the arm is held. Arm values are never derived from controller input.

## Safety behavior

- **Alignment is slow, cancellable, and bounded.** The Auto Catch alignment never exceeds `ALIGN_MAX_XY` (0.06 m/s, below the slow level) on either axis, changes speed by at most `ALIGN_MAX_ACCEL` (0.15 m/s²), and never rotates; `Stop` cancels it at once, and it ends by itself after `ALIGN_TIMEOUT_S` (15 s) or when the egg is lost. Loss of dino-controller input does not stop it (the attendee is not driving), but `Stop`, ESC/window close, Ctrl+C, and the host watchdog still apply.
- **Auto Release is slow, cancellable, and bounded.** Its alignment uses the Auto Catch limits; the arm moves only at `ARM_ENGAGE_SPEED_DEG_S` toward home and the motion's start, and at most `RELEASE_MAX_JOINT_STEP_DEG_PER_S` × frame time per joint during playback, at `RELEASE_PLAYBACK_SPEED`; the base is zero in every arm phase; `Stop` cancels it in the frame it arrives and holds the arm; each arm approach has an 8 s limit.
- **Auto Catch arm motion is slow, cancellable, and bounded.** Every scripted pose move (Auto Catch to the start, catch, and release poses; Auto Release home, motion start, and return home) is synchronized (owner decision, 2026-09-25): all joints move along a straight line in joint space and arrive together, the largest delta at `ARM_ENGAGE_SPEED_DEG_S`, because per-joint limits let a small shoulder delta finish first and the head rose before it tilted down (robot run 2026-09-25); leader engagement stays per joint. The arm moves only toward the start, catch, and release poses, the base is zero in every arm phase, each approach has an 8 s limit, and `Stop` cancels it in the frame it arrives and holds the arm.
- **Stops clear pending rotation.** Input loss, `Stop` and its latch, every mode switch, FSC, and the optional Catch role all reset the encoder rotation budget to zero, so rotation never resumes on its own after a stop.
- **Input lost -> zeros.** Until a valid `state` snapshot is received, after `ready`, `error`, or a sequence gap, and whenever no valid controller message arrives for `CONTROLLER_INPUT_TIMEOUT_S` (0.5 s), the loop sends zero velocities. The reader requests `STATE` every `CONTROLLER_STATE_POLL_INTERVAL_S` (0.2 s) because the firmware is silent while inputs are unchanged.
- **`Stop` latches zeros and a held arm until `Go Go!`; mode switches send zeros for one frame.** See "KachiButton controls". This is a software stop through the signboard process and the loop (tens of milliseconds); the host watchdog remains the last line.
- **No jump on engagement.** The arm approaches the leader at a limited rate before following it; a leader fault holds the arm and forces a new slow approach.
- **Manual Mode needs the arm pose.** The application does not start unless the arm pose can be read at connect; every command, including stop commands, carries a full arm pose.
- **Ctrl+C, ESC/window close, or any loop error -> zeros, then disconnect.** Shutdown sends zero velocities before closing the robot connection, then closes the leader arm, camera, controller, and signboard.
- **Host watchdog is the backstop.** The Pi host stops the base if no command arrives for 500 ms; the application does not rely on it.
